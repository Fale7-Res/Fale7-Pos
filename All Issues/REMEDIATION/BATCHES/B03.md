### FIN-0025 — still present, and wider than the issue says
- `RefundOrderHandler.cs:49-50` runs the replay lookup before the lock (:56-63), and no lookup follows the lock.
- **Permission path:** the clamp at :82 gives 0, so :83 throws `DomainException("لا يوجد مبلغ متبقٍ للاسترجاع.")`.
- **Approval path:** it fails earlier, at :75. `ValidateApproval` (`ApprovalRegistry.cs:123-124`) finds the approval already consumed. This happens even for **partial** refunds.
- The catch at :149-150 does not catch `DomainException`, so the endpoint returns 422 (`Program.cs:1499-1502`).
- The client then marks the operation "refused" (`CashierViewModel.Durability.cs:59-65`).
- The existing concurrent test passes only for a partial refund with permission (`RefundVerticalSliceTests.cs:114-128`).

**RED test.** `RefundVerticalSliceTests.A_same_id_retry_queued_behind_its_own_refund_returns_that_refund(long amount, bool viaApproval)` with cases (20000, false), (20000, true) and (8000, true).
- **Hold the order row lock** from a separate scope: a transaction plus `SELECT … WITH (UPDLOCK, ROWLOCK, HOLDLOCK)`.
- **Start two identical refunds.** Poll `sys.dm_exec_requests WHERE blocking_session_id = @@SPID` until it reaches 2 (about 15 s timeout, otherwise `Assert.Fail`). Then roll back the hold and wait for both.
- **Assert:**
  - both responses are 200;
  - one is a replay; same RefundId and MovementId; the amount matches;
  - one OrderRefunds row and one refund movement;
  - the order's refund amount is correct, and its status is refunded when fully refunded.
- **RED reason:** 422 bodies "لا يوجد مبلغ متبقٍ للاسترجاع." and "اعتماد المدير غير صالح أو لا يطابق العملية.".
- **If the DMV is not visible:** fall back to a fixed delay.

**Fix.** Right after the lock (after :63) and **before** the approval block (:65), add:

```csharp
var completed = await FindExistingAsync(refundKey, ct);
if (completed is not null) return await ToResultAsync(completed, wasReplayed: true, ct);
```

Keep the pre-lock fast path. This is the same pattern as `RecordEmployeeCashOutHandler.cs:65-71`.

### PAYR-0014 — still present in all three handlers
- `RecordDailyWageHandlers.cs`: authorization comes before the dedupe at daily wage :45 vs :54, overtime :90 vs :97 (validation :79), and extra shift :138 vs :146 (validation :127).
- **Ids:**
  - overtime `led-overtime-{RequestId}`;
  - extra shift `led-extra-shift-{RequestId}`;
  - daily wage `led-daily-wage-{EmployeeId}-{BusinessClock.Today()}-{ShiftId??"no-shift"}`.
- Consumed approvals are permanent (`EfApprovalRegistry.cs:63-71`), so a retry with the same approval gets 422 (`Program.cs:848/859/870`).
- **Client:** `EmployeesViewModel.cs:192-196` keeps the request, and the panel stays locked (`CanEditAction` false, no discard).

**Overtime and extra-shift fix.** Compute `id` first, ahead of the guards. Then:

```csharp
var completed = await _db.EmployeeLedgerEntries.AsNoTracking().FirstOrDefaultAsync(e => e.Id == id, ct);
if (completed is not null) return EmployeeQueryService.ToLedgerDto(completed);
```

Also refuse with "مفتاح العملية مستخدم لعملية أخرى." if `completed.EmployeeId != request.EmployeeId`. The orchestrator adopts this hardening.
