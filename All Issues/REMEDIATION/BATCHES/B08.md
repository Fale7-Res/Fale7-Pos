# B08 — No PINs on disk; PIN check without session swap

**Issues:** SEC-0009, SEC-0008 · **Started:** 2026-11-06

## Analysis (falah-analyst)

**Verdict:** READY. No migration and no business-policy question.

**Order of work:**
1. SEC-0009, server side.
2. SEC-0009, client side.
3. SEC-0008(a): PINs are never written to disk.
4. SEC-0008(b): the pending-request store is protected with DPAPI.

The server replay (step 1) is what makes memory-only PIN commands safe to retry.

**Orchestrator scope decision (2026-11-06)**
- **Implement now:** SEC-0009 and SEC-0008(a).
- **SEC-0008(b) is held for the owner.** It needs a new NuGet reference, `System.Security.Cryptography.ProtectedData` 6.0.0, in three projects. The owner asked for no unnecessary dependencies.
  - The package-free alternative is a P/Invoke to `crypt32!CryptProtectData`: about 50 lines, duplicated in both stores.
  - (b) is defence in depth: people who share one Windows account can still decrypt the files.
  - (a) alone closes the PIN exposure. (b) is what protects customer details (name, phone, address) in pending checkouts.

**Contract change:** `ChangePinRequest` gains an optional trailing `RequestId`. This is additive, and a client that does not send it gets today's behaviour, so the server and the clients can be deployed in either order. It follows the precedent of B03's D1 (accepted by the orchestrator).

### SEC-0009 — still present
**Evidence**
- **Client:** `UsersViewModel.Actions.cs:163-174`. When a pending self-service PIN change is retried, the client calls `LoginByPinAsync(NewPin)` to prove the change took effect.
- **Why that is dangerous:** `ApiClient.cs:164-166` installs the new login's token as the shared session token.
  - If the change did not commit and the new PIN is someone else's, the till runs under another person's identity.
  - The proof is also a PIN check that `PinChoiceGuard` does not guard.
- **Server root cause:** `ChangePinRequest` (`UserManagementRequests.cs:23`) has no request id, and `ChangePinHandler.cs:32-73` has no replay check.
  - A committed self-service change, retried, gets 422 "رمز PIN الحالي غير صحيح.".
  - An admin-reset retry spends a second PIN choice and writes a second `pin_changed` row.

**Fix: server** (`ChangePinHandler.cs`, which has an owner diff adding `PinChoiceGuard`; build on top of it)
- `auditId = $"audit-pin-changed-{ActorUserId}-{RequestId}"` when a RequestId is given.
- **Replay first,** before `AssertValidPin`, `ClaimAsync` and the current-PIN check.
  - If a row with that id exists for another action or another user, refuse with "مفتاح الطلب مستخدم لعملية أخرى.".
  - If it exists for this change, return without changing anything.
- Insert the audit row with that `Id` and with `OperationId = RequestId`.
- On `DbUpdateException` or `DomainException`, check the replay again (the pattern of `CreateUserHandler:64-102`).
- Do not catch `PinChoiceLimitException` or `InvalidOperationException`.
- Optional: refuse a RequestId longer than about 100 characters, checked after the replay lookup.

**Fix: client** (`UsersViewModel.Actions.cs`, which has an owner diff; keep it)
- The request carries `RequestId = $"change-pin-{Guid:N}"`.
- Send it with `r => _session.Api.ChangePinAsync(r)`.
- Delete `wasPending` and the whole proof block.

**RED tests**
- In `UserManagementVerticalSliceTests` (owner diff, additive; the helper gets an optional requestId):
  - `Retrying_a_committed_self_service_pin_change_with_the_same_request_id_replays`. Assert: 200; the new PIN logs in; 1 `pin_changed` row; 1 `pin_choice` row for the user.
  - `Retrying_an_admin_pin_reset_with_the_same_request_id_does_not_spend_a_second_pin_choice`. Compare the counts before and after.
  - `A_pin_change_request_id_reused_for_another_user_is_refused`. Assert: 422, and B's PIN is unchanged.
- Client: `UserWorkflowTests.Retrying_an_unconfirmed_self_pin_change_keeps_the_session_token_and_resends_the_same_request`. Assert:
  - exactly 1 login;
  - every later request carries `Bearer session-token`;
  - 2 identical change-pin bodies with a requestId;
  - the operation is resolved, and the current user is unchanged.

**Intentional changes to existing tests** (they encoded the defect)
- `Lost_self_pin_confirmation_is_reconciled_to_the_same_user_without_rewriting_the_pin` asserts `proofs == 1`. The new test replaces it.
- `A_pin_proof_for_a_different_user_does_not_confirm_the_pending_change`: drop the dead login branch and rename it to `A_refused_retry_of_an_unconfirmed_pin_change_stays_pending`.

### SEC-0008 — still present
**Evidence**
- Both `RetainedRequestStore.cs` files (Cashier and CallCenter, identical apart from the namespace) write plain JSON to `%LOCALAPPDATA%\Falah\pending-operations\<station>` (:59-80).
- `UsersViewModel.Actions.cs:13-14` gives `users.create` (InitialPin) and `users.change-pin` (CurrentPin, NewPin) durable keys.
- Pending checkouts carry the customer's name, phone and address (`CallCenterViewModel.Checkout.cs:68-72,181`; `CashierViewModel.Durability.cs:94-99`).

**Fix (a), in scope now**
- `_pendingCreate` and `_pendingPin` become memory-only (no owner key). The path that writes nothing to disk is already tested.
- After a power cut nothing is recovered for these. This is acceptable: they are not money commands, and the user list or a login shows the outcome.
- New `ForgetRetiredPinRequests(store)` removes old `users.create` and `users.change-pin` files. Cashier `App.xaml.cs` calls it right after the store is created, before `MainViewModel` lists recovered operations.

**RED tests** (new `tests/Falah.Client.Tests/PinsAtRestTests.cs`, in `[Collection(RetainedRequestStorageCollection.Name)]`)
- `An_unconfirmed_pin_change_writes_no_pin_to_disk`
- `An_unconfirmed_user_creation_writes_no_pin_to_disk`
- `A_pin_request_left_by_an_earlier_version_is_removed`

**Fix (b), held for the owner** (DPAPI, CurrentUser scope, fixed app entropy)
- The envelope keeps `Type` and `SavedAtUtc` readable. `Payload` is replaced by `Protected` (base64).
- Legacy plain files are rewritten protected on `Load` or `List`.
- A file that cannot be decrypted is kept and reported.
- Guard with `OperatingSystem.IsWindows()`.
- RED tests: `RetainedRequestDurabilityTests.A_pending_request_is_not_readable_on_disk`, `A_pending_file_written_before_protection_is_recovered_and_then_protected`, and `CallCenterDurabilityTests.A_checkout_left_in_flight_does_not_expose_the_customer_on_disk`.
- **Risk:** an administrator resetting the Windows password makes the protected files unreadable.

### Regression
- **Integration:** UserManagementVerticalSlice, PinChoiceOracle, LoginPinGuessing, ApprovalPinGuessing, Authentication, Auth, DemoCredentials.
- **Client:** all of Falah.Client.Tests.
- **Builds:** CashierWinUI x64. CallCenterWinUI x64 only for (b).

### Residual risks
- A memory-only `users.create` whose commit was not confirmed before a restart: re-creating the user with the same PIN is refused as "PIN in use", and it writes a false `pin_collision` alarm.
- Out of scope: the print agent's PIN in its local secrets file (`AgentOptions.cs:179-201`) is deliberate.
- The issue's "server-issued change ticket" is not needed once the server replays.

## Final implementation — 2026-11-07
Used Windows DPAPI directly (no new package), CurrentUser scope and fixed application entropy. Envelope metadata stays readable; payloads encrypted. Legacy JSON and interrupted .json.tmp files migrate atomically. Unreadable protected files remain in place, are reported, and block new transactions until the original Windows profile/key is restored.
