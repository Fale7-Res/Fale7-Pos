## 1. Original source references

Remediation loop, batch B02 analysis (All Issues/REMEDIATION/BATCHES/B02.md), confirmed by the orchestrator against source.

## 2. Affected components

PayrollViewModel (CashierWinUI); payroll run DTO status values; client tests fixtures

## 3. Current code evidence

- **Client:** `src/Falah.Client.CashierWinUI/ViewModels/PayrollViewModel.cs:112-118`. `NextStatus` switches on the lowercase literals "draft", "calculated" and "reviewed".
- **Client:** `:129`, `IsApprovedAndUnpaid => SelectedRun?.Status == "approved"`.
- **Server:** writes capitalised enum names.
  - `src/Falah.Infrastructure/Employees/CreatePayrollHandler.cs:70`: `Status = nameof(PayrollRunStatus.Draft)`.
  - `TransitionPayrollHandler.cs:55`: `targetStatus.ToString()`.
  - `src/Falah.Infrastructure/Employees/PayrollQueryService.cs:14` returns `r.Status` unchanged.
  - `tests/Falah.Server.IntegrationTests/PayrollVerticalSliceTests` asserts "Draft" and "Approved".

## 4. Relevant historical evidence

Client tests use lowercase fixtures (`FinalVerificationTests.cs:208,222`, `ManagementWriteSafetyTests.cs:63`), which hides the mismatch. `StatusRank` and `GeneralStatusLabelConverter` lower-case first and are unaffected.

## 5. Expected behaviour

The payroll screen offers the next step for a real run (Draft → Calculated → Reviewed → Approved) and opens the pay dialog for an Approved run.

## 6. Actual code-supported behaviour

For server-returned statuses, NextStatus is null, so the advance button is hidden (bound to NextStatusLabel); IsApprovedAndUnpaid is false, so the pay dialog never opens.

## 7. Root cause

Case-sensitive comparison against a different casing convention than the server's enum names.

## 8. Business impact

Payroll cannot be advanced or paid from the WinUI client against a live server.

## 9. Reproduction / failure scenario

Create a payroll run on a live server; select it on the payroll screen; no advance button and no pay action.

## 10. Existing safeguards

None identified beyond those noted in the evidence.

## 11. Missing safeguards

Case-insensitive comparison; client tests using server-shaped data.

## 12. Recommended remediation

Normalise the status once (e.g. `SelectedRun?.Status?.ToLowerInvariant()`) before the switches and comparisons, or compare with `StringComparison.OrdinalIgnoreCase`; change the client test fixtures to the server's casing.

## 13. Alternative approaches

Return a canonical lowercase wire value from the server (contract change affecting tests and other readers) — not preferred.

## 14. Required regression tests

Client view-model tests with "Draft"/"Approved" (server casing): NextStatus and CanOpenPay behave correctly.
