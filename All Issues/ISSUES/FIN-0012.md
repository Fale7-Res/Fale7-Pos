## 1. Original source references

Copilot register FIN-005

## 2. Affected components

PayPurchaseHandler

## 3. Current code evidence

src/Falah.Infrastructure/Purchasing/PayPurchaseHandler.cs:61-66 computes `outstanding` before the transaction (:73); :95-97 writes paid/remaining from that stale value; purchase row has no lock or concurrency token (FalahDbContext Purchase mapping).

## 4. Relevant historical evidence

No additional historical evidence beyond the sources listed.

## 5. Expected behaviour

Total payments never exceed the invoice outstanding.

## 6. Actual code-supported behaviour

Two payments read the same outstanding and both succeed.

## 7. Root cause

Check-then-act outside the transaction.

## 8. Business impact

Supplier overpaid; invoice cache wrong.

## 9. Reproduction / failure scenario

Two clerks pay 60% each at the same time.

## 10. Existing safeguards

Treasury account lock serialises same-account spends but uses the stale outstanding.

## 11. Missing safeguards

Purchase row lock or rowversion.

## 12. Recommended remediation

Lock the purchase row inside the transaction and recompute outstanding.

## 13. Alternative approaches

No meaningful alternative identified.

## 14. Required regression tests

Parallel 60% payments → one refused.
