## 1. Original source references

All Issues Mission A (2026-11-05)

## 2. Affected components

InventoryViewModel count sheet; RecordCountAdjustmentHandler; checkout stock deduction

## 3. Current code evidence

src/Falah.Client.CashierWinUI/ViewModels/InventoryViewModel.cs:331-337 variance = `counted − Item.BalanceMilliUnits` (balance from the last load); :470-474 posts `Math.Abs(difference)` with In/Out; src/Falah.Infrastructure/Inventory/StockMovementHandlers.cs:26-69 records the delta as given (no counted total, no as-of time).

## 4. Relevant historical evidence

No additional historical evidence beyond the sources listed.

## 5. Expected behaviour

After the count, system stock equals what was physically counted.

## 6. Actual code-supported behaviour

Sales (or receipts) posted between loading the sheet and the physical count are applied twice.

## 7. Root cause

Client computes the delta from a stale snapshot; the server receives only the delta.

## 8. Business impact

Stock silently wrong after every count taken during service.

## 9. Reproduction / failure scenario

Load sheet (balance 10 kg); sell 2 kg; count shelf = 8 kg; variance posted −2 kg → system 6 kg.

## 10. Existing safeguards

Replay-safe per sheet line (request id = sheet id + item).

## 11. Missing safeguards

Counted total with as-of timestamp, or server-side delta.

## 12. Recommended remediation

Send the counted total; server computes delta against the balance at submission (or at a recorded as-of time).

## 13. Alternative approaches

Refresh balances immediately before submission and warn on change.

## 14. Required regression tests

Count during concurrent sale → final balance equals counted.

## 17. Acceptance criteria

Final balance = counted quantity.

## 18. Remaining uncertainty

Whether counts are done during service.
