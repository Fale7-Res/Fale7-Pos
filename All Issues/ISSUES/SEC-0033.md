> The defect is present in current source as described.

## 1. Original source references

Remediation loop, batch B07 analysis (All Issues/REMEDIATION/BATCHES/B07.md). The orchestrator confirmed on 2026-11-06 that the cited route handlers take no HttpContext and so carry no gate.

## 2. Affected components

Program.cs order and delivery GET routes; OrderDetailsDto; DeliveryDto

## 3. Current code evidence

These routes in `src/Falah.Server/Program.cs` have no permission check:
- `/api/orders/{id}` (:1600) and `/api/orders/lookup` (:1608), which return `OrderDetailsDto` with the customer name, phone and address;
- `/api/delivery/board` (:1425), `/api/delivery/ready` (:1428), `/api/delivery/drivers/{driverId}/active` (:1431) and `/api/delivery/{id}` (:1448), which return `DeliveryDto` with the customer fields.

## 4. Relevant historical evidence

Owner decision 2026-11-06: customer data is readable by order takers only (pos/delivery). CUS-0001 (batch B07b) gates the customer routes themselves.

## 5. Expected behaviour

Only order takers (`pos`, `delivery_manage`) and `all` receive customer details from these reads.

## 6. Actual code-supported behaviour

Any authenticated session receives the data, including a print agent or an HR-only account.

## 7. Root cause

The order and delivery reads were left ungated when the customer routes were scoped.

## 8. Business impact

Customer personal data leaks to station and back-office accounts, contrary to the owner's decision.

## 9. Reproduction / failure scenario

Log in as a print-agent account and call GET /api/orders/lookup?orderNumber=... The response includes the customer's phone and address.

## 10. Existing safeguards

Session authentication only.

## 11. Missing safeguards

A permission gate placed first in each route.

## 12. Recommended remediation

Gate the routes on `pos` or `delivery_manage`, with the gate first.
- Check each caller first: Cashier till (`pos`), Call Center (`pos`), WPF client, DeliveryViewModel (`delivery_manage`).
- Where a screen that is not an order taker needs the order, strip the customer fields instead of refusing.

## 13. Alternative approaches

Strip the customer fields on every route for callers without `pos` or `delivery_manage`, instead of refusing.

## 14. Required regression tests

Integration test:
- a print-agent session and an HR session get 422, or no customer fields, from each route;
- a cashier and a `delivery_manage` user get the customer fields.

## 15. Related issues

[CUS-0001](CUS-0001.md); [ARCH-0001](ARCH-0001.md)

## 16. Dependencies and prerequisites

B07b (CUS-0001 gating conventions). The ARCH-0001 allow-list carries these routes as FOLLOW-UP.

## 17. Acceptance criteria

The ARCH-0001 enumeration test no longer needs FOLLOW-UP entries for these routes.

## 18. Remaining uncertainty

Caller compatibility per route has not been traced exhaustively.
