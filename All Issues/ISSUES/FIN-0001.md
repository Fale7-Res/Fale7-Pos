## 1. Original source references

Copilot register FIN-001 (reports from another tool/GitHub Copilot Work/Final-Handoff/ALL_VERIFIED_FINDINGS.json); INDEPENDENT_AUDIT/02 (mechanism corrected); PRODUCTION_RESILIENCE_AUDIT/12 SC-08

## 2. Affected components

CheckoutOrderHandler; ConfirmElectronicPaymentHandler; EfFinancialJournal; POST /api/orders/confirm-electronic-payment

## 3. Current code evidence

src/Falah.Infrastructure/Orders/CheckoutOrderHandler.cs:148-153 starts journal key `sale-{CheckoutRequestId}` for any checkout that does not defer all money (a split is not deferred, CheckoutRules.cs:66-70); src/Falah.Infrastructure/Orders/ConfirmElectronicPaymentHandler.cs:75-78 calls `journal.TryStart(saleKey, "sale")` with the SAME key; src/Falah.Infrastructure/Persistence/EfFinancialJournal.cs:22-27 returns false when the key exists, so the handler throws ConfirmConflictException, caught at :89-95 and re-thrown as "needs manual review".

## 4. Relevant historical evidence

Copilot described it as a SqlException unique-constraint crash; the current code raises a handled conflict instead (INDEPENDENT_AUDIT correction). No test confirms a split order (tests/Falah.Server.IntegrationTests/ConfirmElectronicPaymentTests.cs uses SplitPayments: null).

## 5. Expected behaviour

Confirming the pending electronic leg of a split order posts exactly one treasury movement for that leg and marks the order paid.

## 6. Actual code-supported behaviour

Every confirmation of a split order's electronic leg is refused with a "manual review" conflict; the order stays unpaid forever.

## 7. Root cause

The financial journal is keyed per order (`sale-{id}`), not per payment leg; split checkout already consumed the key for the cash leg.

## 8. Business impact

Split orders with an electronic leg can never be completed; collected-sales and pending-electronic figures stay wrong; operators have no tool to resolve the conflict.

## 9. Reproduction / failure scenario

Checkout 100 ج cash + 200 ج InstaPay; customer's transfer arrives; cashier presses confirm → 409 conflict "يحتاج مراجعة يدوية".

## 10. Existing safeguards

Confirm is idempotent and locked for single-method orders (UPDLOCK at ConfirmElectronicPaymentHandler.cs:53-56).

## 11. Missing safeguards

Leg-level journal key; a test for split confirmation.

## 12. Recommended remediation

Key the confirmation journal entry by leg (e.g. `sale-{CheckoutRequestId}-electronic`), or reuse the order's existing journal row and post only the electronic movement; part of the split-payment model fix (see [FIN-0002](FIN-0002.md), [FIN-0003](FIN-0003.md), [FIN-0004](FIN-0004.md)).

## 13. Alternative approaches

Model payment legs as their own rows (OrderPayments) with per-leg status and idempotency key.

## 14. Required regression tests

Integration: split cash+InstaPay checkout → confirm → exactly one InstaPay movement for the leg amount; repeat confirm → replay; concurrent confirm → one movement.

## 15. Related issues

[FIN-0002](FIN-0002.md); [FIN-0003](FIN-0003.md); [FIN-0004](FIN-0004.md); [FIN-0005](FIN-0005.md); [ARCH-0003](ARCH-0003.md)

## 16. Dependencies and prerequisites

Decide the split-payment data model first (one change closes [FIN-0001](FIN-0001.md)..0005).

## 17. Acceptance criteria

Split confirm returns 200; one movement with the leg amount; order IsPaid; reports show the leg collected.

## 18. Remaining uncertainty

None about the code path; frequency of split orders unknown.
