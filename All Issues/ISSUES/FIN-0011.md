## 1. Original source references

Copilot register FIN-011

## 2. Affected components

OpenShiftHandler; ReceivePurchaseHandler; TreasuryBalanceQuery

## 3. Current code evidence

src/Falah.Infrastructure/Shifts/OpenShiftHandler.cs:57-59 (lock read) vs :75 (BeginTransaction); src/Falah.Infrastructure/Purchasing/ReceivePurchaseHandler.cs:75-79 vs :97. Six other money handlers do it inside the transaction (AddExpenseHandler.cs:70-78, SafeDropHandler.cs:59-67, TransferHandler.cs:56-64, WithdrawalHandler.cs:56-64, RefundOrderHandler.cs:56/92, PayPurchaseHandler.cs:73/80).

## 4. Relevant historical evidence

No additional historical evidence beyond the sources listed.

## 5. Expected behaviour

The UPDLOCK/HOLDLOCK balance read holds until the spend commits.

## 6. Actual code-supported behaviour

The lock is released at the end of the implicit statement transaction; concurrent spends can overdraw main.

## 7. Root cause

Lock read placed before BeginTransactionAsync.

## 8. Business impact

Main treasury can go negative.

## 9. Reproduction / failure scenario

Shift open float 500 ج and a 500 ج withdrawal in parallel against 600 ج.

## 10. Existing safeguards

Close evaluator flags negative protected balances at day close.

## 11. Missing safeguards

Correct ordering.

## 12. Recommended remediation

Move both reads inside the transaction.

## 13. Alternative approaches

No meaningful alternative identified.

## 14. Required regression tests

Parallel float + withdrawal exceeding balance → one refused.
