> The defect is present in current source as described.

## 1. Original source references

Remediation loop, batch B03 analysis (All Issues/REMEDIATION/BATCHES/B03.md).

## 2. Affected components

RecordDailyWageHandler, RecordOvertimeHandler, RecordExtraShiftHandler; EmployeeLedgerPoster; ManagerApproval Consumed concurrency token

## 3. Current code evidence

`src/Falah.Infrastructure/Employees/RecordDailyWageHandlers.cs` — the three handlers run without a transaction or a per-employee lock. Two concurrent requests with the same id both pass the replay/dedupe check. The loser then hits:
- a primary-key `DbUpdateException` on the ledger row; or
- the `Consumed` concurrency token on the approval (`src/Falah.Infrastructure/Persistence/FalahDbContext.cs:184`).

Neither is handled, so the global exception handler returns 500.

## 4. Relevant historical evidence

Cash-out (`RecordEmployeeCashOutHandler.cs:94-104`) uses an UPDLOCK transaction and replays on conflict; these handlers do not.

## 5. Expected behaviour

The second concurrent same-id request returns the committed entry (replay).

## 6. Actual code-supported behaviour

500; the client treats 5xx as outcome unknown and keeps retrying (see [API-0003](API-0003.md)).

## 7. Root cause

No transaction/lock and no conflict-to-replay mapping.

## 8. Business impact

Low: only on concurrent double submission; no double credit (the primary key prevents it), but a confusing error and a stuck kept request.

## 9. Reproduction / failure scenario

Two identical overtime requests sent at the same instant.

## 10. Existing safeguards

The deterministic primary key prevents a double credit.

## 11. Missing safeguards

A transaction with a per-employee lock, or mapping the conflict to a replay.

## 12. Recommended remediation

Wrap each handler in a transaction with the same per-employee UPDLOCK used by cash-out, and on DbUpdateException/DbUpdateConcurrencyException re-read the entry by id and return it as a replay.

## 13. Alternative approaches

No meaningful alternative identified.

## 14. Required regression tests

`Task.WhenAll` of two identical overtime requests → both 200, one ledger row.

## 16. Dependencies and prerequisites

B03 (PAYR-0014) replay ordering.

## 17. Acceptance criteria

Concurrent same-id requests never return 500.

## 18. Remaining uncertainty

The race was not executed.
