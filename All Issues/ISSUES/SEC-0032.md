> Remediation implemented; see current test evidence below.

## 1. Original source references

Remediation loop, batch B09 analysis (All Issues/REMEDIATION/BATCHES/B09.md). The orchestrator confirmed the cited lines on 2026-11-06.

## 2. Affected components

LoginAttemptGuard (BeginAsync / Attempt); `/api/auth/login-by-pin` endpoint

## 3. Current code evidence

- `src/Falah.Infrastructure/Authorization/LoginAttemptGuard.cs:89-102`: `BeginAsync` records a wrong PIN for the source before the PIN is checked. Only `Attempt.Succeeded()` (:266) releases that reservation.
- `src/Falah.Server/Program.cs:1974-2010`: after `BeginAsync`, several steps can throw before the PIN check is decided:
  - the user query (`ToListAsync`);
  - the audit `SaveChangesAsync`;
  - `sessions.IssueAsync`, after a correct PIN;
  - cancellation, when the client disconnects.

  Only `LoginThrottledException` is caught. Any other exception leaves the reservation counted, and the global handler returns 500.
- A correct PIN whose session issue fails is not affected: `Succeeded()` is called before `IssueAsync`.

## 4. Relevant historical evidence

The B09 print-agent analysis found that an agent retrying through server errors would use up its machine's wrong-PIN allowance.

## 5. Expected behaviour

Only a PIN that was checked and found wrong counts against the source.

## 6. Actual code-supported behaviour

Database timeouts, failures to write the audit row and client cancellations each count as a wrong PIN. These are 5 per 15 minutes and 20 per day per source.

## 7. Root cause

The guard reserves first, so that concurrent guesses cannot overrun the limit, but it has no release path for outcomes that are not decided.

## 8. Business impact

A database hiccup during the morning login rush can lock a till PC out of logging in. This is low impact on its own, but it compounds with the print agent's retry policy (PRT-0006, PRT-0012).

## 9. Reproduction / failure scenario

1. Make the user query time out, for example while the database is under a long blocking lock.
2. Repeat 5 times from one PC. That PC is now refused with 429, although no wrong PIN was ever entered.

## 10. Existing safeguards

The per-day and per-15-minute limits are generous, and an administrator can see the sources.

## 11. Missing safeguards

Release the reservation when the attempt ends without a decision.

## 12. Recommended remediation

- Add `Attempt.Abandon()`, which removes the stamp exactly like `Succeeded()`.
- Release the stamp in a `try/finally` unless the attempt was decided to be wrong.
- Never release it after the wrong-PIN branch.

## 13. Alternative approaches

Reserve after the user query. This narrows the window but does not close it.

## 14. Required regression tests

Integration test: a login whose user query throws (fault injection through a DbCommandInterceptor) does not count. After 6 such failures, a correct PIN from the same source still logs in.

## 15. Related issues

[PRT-0012](PRT-0012.md); [PRT-0006](PRT-0006.md)

## 16. Dependencies and prerequisites

None.

## 17. Acceptance criteria

Only decided wrong PINs count against a source.
