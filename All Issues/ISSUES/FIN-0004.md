> The defect is present in current source as described.

## 1. Original source references

Copilot register FIN-MULTI-ELEC-001; INDEPENDENT_AUDIT/02

## 2. Affected components

CheckoutRules.SelectElectronicLeg; FinancialRules.AssertSplitPaymentAllocation; CheckoutOrderHandler

## 3. Current code evidence

src/Falah.Domain/Orders/CheckoutRules.cs:56-62 keeps only `.First()` electronic split; src/Falah.Domain/Financial/FinancialRules.cs:13-24 allows InstaPay and Wallet together (methods only need to be distinct); src/Falah.Infrastructure/Orders/CheckoutOrderHandler.cs:259-260 skips posting every electronic split.

## 4. Relevant historical evidence

No additional historical evidence beyond the sources listed.

## 5. Expected behaviour

Either refused at checkout, or both electronic legs tracked as pending.

## 6. Actual code-supported behaviour

Only the first electronic leg becomes the pending claim; the second is neither posted nor pending.

## 7. Root cause

Single ElectronicPayment per order.

## 8. Business impact

Money unaccounted for; reports and treasury understate.

## 9. Reproduction / failure scenario

100 ج InstaPay + 100 ج Wallet split → only InstaPay 100 ج pending.

## 10. Existing safeguards

Allocation must equal total.

## 11. Missing safeguards

Rejection of >1 electronic leg.

## 12. Recommended remediation

Reject more than one electronic leg in AssertSplitPaymentAllocation until legs are modelled.

## 13. Alternative approaches

Model legs individually (see [FIN-0001](FIN-0001.md)).

## 14. Required regression tests

Integration: InstaPay+Wallet split → 422 (or two tracked legs).

## 15. Related issues

[FIN-0001](FIN-0001.md)

## 16. Dependencies and prerequisites

None.

## 17. Acceptance criteria

No checkout can lose a leg.

## 18. Remaining uncertainty

Whether the client UI ever offers this combination.
