## Runtime cost map

Cashier WinUI and optional Call Center are separate processes. Both communicate with the existing ASP.NET Core server; only the server uses EF Core/SQL Server. Print Agent is an independent HTTP worker, normally one per configured route. A cashier-only station does not need to run Call Center merely to take counter orders. Separating roles onto other PCs preserves features and can distribute resources, but makes LAN/server availability operational dependencies.

Startup is not a safe benchmark to rerun indiscriminately: `src/Falah.Server/Program.cs:206-215` applies migrations, can change READ_COMMITTED_SNAPSHOT and calls the seeder. Its registered scheduled backup worker can later write records/files and prune backups. Any future timing must target an explicitly approved isolated database with known lifecycle and backup settings. None of those paths was executed here.

Client initialization (`CashierViewModel.State.cs:87-112`) fetches current shift, then settings, then menu if a shift is open; `CashierViewModel.LoadMenuAsync:109-152` fetches menu then tax rules. These serial dependencies add network latency. Parallelizing independent reads may help after lifecycle and error-state tests, but must preserve the current shift/menu gate, tax selection and state notifications. The scoped server DbContext must not be used concurrently with a blind Task.WhenAll optimization.

## Source-supported bottlenecks and counterevidence

1. **Menu and best-seller materialization — PERF-CAND-01.** `MenuQueryService.GetMenuAsync:17-43` batches active categories, product data, rules and image-version stamps. It deliberately avoids photo byte columns. `LoadProductsInMenuOrderAsync:57-74` sorts narrow product IDs separately from full rows and orders variants in memory; claiming the old full-row sort remains would be wrong. `LoadBestSellerIdsAsync:85-106` transfers recent order-item pairs before grouping and Take(12). The final Take caps shortcut count, not transferred sales volume. The lower time bound is finite, but a busy fortnight can still contain many rows. A server-side equivalent aggregate is a useful candidate, with cancelled-order, availability, tie-order and Cairo business-window equivalence tests. No observed timeout is asserted.

2. **UI search allocation — PERF-CAND-03.** `CashierViewModel.RefreshVisibleProducts:80-101` rebuilds the product-icon lookup and all matching tile/offer objects on each search change, clearing and repopulating ObservableCollection on the UI path. Measure before optimizing. Precomputed catalog metadata and a short presentation-only debounce can reduce repeated work; preserve culture-aware Arabic search, selection and best-seller deduplication. This source evidence does not establish disabled GridView virtualization or a measured frame-rate defect.

3. **Image retention — PERF-CAND-02.** `Converters/ImageUriToSourceConverter.Convert:807-818` uses a static dictionary keyed by versioned URL with no eviction. The 320-pixel decode width is an existing mitigation and cache reuse avoids redownloads during tile rebuilds. Old revisions/server URLs remain strongly referenced for process life. This is confirmed retention policy, not proof of a native leak or an out-of-memory incident. The 512 KiB encoded-image cap in `ProductImageRules:17-58` and signature checks do not themselves cap decoded height/pixels; decoded/native allocation must be measured. A bounded cache must not churn while active tiles still need an image.

4. **Reports and dashboard — PERF-CAND-05/06.** `ReportingQueryService.LoadSalesOrdersAsync:38-55` Includes order items then materializes every matching order; null date and shift filters allow history-wide reads. Sales/tax map full entities into domain objects. `OwnerDashboardQueryService.GetAsync:38-73` composes multiple sequential report/treasury/stock/obligation/people/health reads and current/prior trend data. This can repeat work and round trips, but is not proof of a per-row N+1 query. Aggregation must preserve frozen totals, refunds, COD custody, mixed payments and financial reconciliation; a faster incorrect total is unacceptable. Project only needed fields, reuse a consistent reporting snapshot, and bound detailed presentation without truncating totals.

5. **Employee ledger — PERF-CAND-07.** `EmployeeLedgerPoster.GetCurrentBalanceAsync:15-26` transfers all employee credit/debit deltas and also includes staged Added entries in the current DbContext. Repeated postings grow with ledger history. A database aggregate may help, but omitting staged entries changes balances. Retain idempotency and obtain independent financial/concurrency verification before an implementation change.

6. **Health cadence — PERF-CAND-04/04B.** Cashier `MainViewModel:32-35,59-63,72-77` and Call Center `MainViewModel:31-40,49-54` independently schedule async probes every five seconds without an in-flight gate. HTTP timeout is ten seconds in Cashier `ApiClient:28-31`. A slow probe can overlap another tick; Stop prevents subsequent state updates but does not cancel a started request. Healthy nominal cadence is approximately 12 requests/minute per open station, or 24 with both clients: this is an arithmetic model, not a packet capture. `/health` performs a DB connectivity check (`Program.cs:2251-2252`); a socket-only substitute would weaken readiness semantics. Propose single-flight/cancellable probing, with recovery and close-during-request tests.

7. **Print backlog and throughput — PERF-CAND-08/09.** `PrintJobQueryService.ListPendingJobsForRouteAsync:38-42` returns the whole pending route; overview only takes 60 after materializing nonsucceeded jobs plus recent successes (`:50-94`). The model already has a Route/Status index (`FalahDbContext.cs:370`); avoid falsely reporting no index. CreatedAt sort coverage and actual plans still need SQL evidence. Print Agent drains serially and delays after a full drain (`Program.cs:135-154`), so a busy queue's interval is drain time plus the configured delay, not exactly three seconds. Default empty-queue polling is approximately 20 requests/minute/agent; R idle routes imply about 20R polling requests/minute before health/work traffic. Per-job compose/report adds more. Serial transport is necessary for one paper path. Bounded paging with durable claim/lease requires coordination with PRT-001, rather than unsafe parallel sends or deletion of failed history.

8. **Raster CPU/memory — PERF-CAND-10.** `BitmapTicketRenderer.Render:83-101` renders/disposes one cut segment at a time but accumulates the output stream and returns a copy. `RenderSegment:244-395` allocates bitmap height from wrapped content. `WriteRaster:500-535` calls GetPixel per pixel, creates a bool grid, optional protected/grown grids, and packed output. Peak allocation scales with width × height, plus native bitmap, text/fonts, and accumulated payload. A 576×10,000 segment has 5.76 million pixels; 32-bit bitmap storage alone is about 23 MB, while each byte-sized bool grid is about 5.76 MB, excluding array/native overhead. This is a dimensional estimate, not an observed ticket. Exception paths before the normal font cleanup loop can delay resource release. Normally disposed bitmaps/Graphics/format objects contradict a blanket leak claim. LockBits or bounded raster strips deserve profiling with exact Arabic/QR/inversion/cut regression comparisons; never crop receipts or alter legal content to save memory.

9. **Authentication cost has an existing mitigation — PERF-CAND-11.** `SessionService.ResolveAsync:46-73` reads token then active user, but LastSeen writes occur only after a one-minute interval, not on every poll. TokenHash is uniquely indexed (`FalahDbContext.cs:191`). Do not introduce stale authorization caches or disable writes/security as a speculative optimization. Parallel resolutions may race on the refresh threshold; impact is unmeasured.

10. **Backup and disk contention.** Scheduled backups check after a 90-second grace, every 30 minutes, default maximum age 20 hours and retention 60 (`ScheduledBackupService:38-44,63-121`). Backup/verification/pruning compete with foreground SQL/storage. They are intended maintenance, not evidence of a malicious timer. Capacity must budget actual backup size × retained copies, log growth, images and free-space headroom. Do not disable production backups merely to improve benchmark numbers. No SQL connection-pool exhaustion, deadlock, memory grant or sustained disk contention was observed during this review.

## Hardware profiles: procurement hypotheses pending certification

**A measured minimum supported configuration cannot be honestly certified from current evidence.** The following are starting test/procurement envelopes, not a guarantee, vendor minimum, or permission to purchase based on a proven result. No features are removed to meet them.

| Role | Provisional low-end validation target | Recommended starting production envelope | Acceptance boundary |
|---|---|---|---|
| Client-only cashier or Call Center | Modern x64 CPU with at least two physical cores; 8 GB RAM; SSD | Four capable physical cores; 8–16 GB RAM; SSD | One station process, remote SQL/API; test large menus/images, keyboard/touch and outage recovery |
| Combined cashier + local API/SQL + print routes | At least four physical x64 cores; 8 GB is a stress-test target, not approved production minimum | Four or more capable cores; 16 GB RAM; SSD, UPS and separate verified backup destination | Must pass peak workload, reporting and long-raster tests simultaneously, with reserve for OS/SQL cache |
| Shared backend for multiple stations | Four cores/16 GB starting experiment | Four–eight capable cores; 16–32 GB RAM; SSD and protected backup/storage | Size against concurrent stations, orders, history and maintenance; no station/order ceiling certified |

CPU clock/core count alone does not establish responsiveness. Avoid treating very old low-power two-core hardware, 4 GB RAM, a spinning HDD or a stripped Windows image as a supported full-system target without measurement. Moving optional Call Center onto its own workstation distributes load without deleting its functionality; a server outage still affects clients. No dedicated GPU requirement was demonstrated by this source review; driver stability and target display/DPI must be validated.

Use an SSD with at least 128 GB total as a provisional client starting point and at least 256 GB for a combined host; capacity labels do not establish free usable space. Reserve an initial 20 GB free operational margin plus the separately measured database, transaction-log, retained-backup and image budget, and alert before that margin is consumed. These are engineering planning values, not measured footprints. Backups on another partition of the same drive are not independent failure protection. Build machines additionally require SDK/toolchain/package caches and substantially more temporary space; build footprint is not the deployed application footprint. No complete publish-directory size was established here.

## Windows, .NET, SQL and deployment dependencies

The active WinUI projects declare `net8.0-windows10.0.19041.0`, minimum `10.0.17763.0`, x64/win-x64, unpackaged deployment and `WindowsAppSDKSelfContained=true`. The latter bundles Windows App SDK components; it does not prove the .NET runtime is self-contained. Backend/Print Agent target net8.0. Historical binaries were inspected as x64. Keep the .NET 8/ASP.NET Core runtime for the server, appropriate Windows desktop/.NET runtime dependencies for clients, and VC/native Windows components required by the actual deployment output. Full SDK/Visual Studio is a build prerequisite, not automatically a restaurant runtime prerequisite.

Windows 7 and 32-bit Windows are not current deployment targets: the selected WinUI target/minimum build and RID exclude them. Replacing the frontend solely for Windows 7 is not recommended. The old WPF project name does not make this .NET 8 solution Windows 7 compatible.

Microsoft documents Windows App SDK compatibility with Windows 10 1809/build 17763 and later, conditional on Windows servicing SKU/channel. Binary compatibility does not imply a particular old Windows 10 installation remains supported. Verify the exact edition/build, servicing/ESU entitlement, patches, WinUI/native dependencies, graphics/text components and SQL support before accepting any lightweight installation. No Windows services or system components were removed or installed. [Windows App SDK supported releases](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/support), [Windows 10 Home/Pro lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro).

As retrieved 2026-10-17, Microsoft's current table lists .NET 8 patch 8.0.32 and end of support 2026-11-10. The historical runtime discovery recorded 8.0.31, so it is not evidence of current patch compliance. Plan an owner-approved servicing/upgrade compatibility project before production; no upgrade was performed during this audit. [Microsoft .NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core).

The implemented EF provider requires SQL Server. Keep the approved isolated LocalDB environment for development; do not replace an existing production instance, attach its files, or infer a production service deployment from a user-scoped LocalDB success. Production SQL edition/version sizing, supported OS combination, service identity, storage and backup recovery need explicit deployment validation. Exact SQL edition memory/database limits vary and were not independently certified here. Preserve the existing connection target and financial safety rules.

Use stable wired LAN for shared backend/printer roles; provision compatible Windows spooler/driver or configured network/serial transport per actual printer. No fixed bandwidth or latency SLA is measured. Reliable DNS/addressing, time, power and reconnect behavior matter. Physical throughput, paper width, Arabic glyph quality, cutter behavior and spooler acceptance remain separate hardware tests.

## Repeatable validation matrix — NOT EXECUTED here

All workload creation/API authentication/printing requires the owner's approved isolated environment and disclosure of generated records. Never benchmark an unknown restaurant database. Read-only process sampling must avoid command-line credentials and user/customer payloads. Synthetic ticket render-only tests can avoid physical output; they still need an explicit controlled test harness.

| Investigation | Controlled method and recorded evidence | Proposed acceptance / regression protection |
|---|---|---|
| Cold/warm startup | Timestamp process launch, first rendered PIN screen and authenticated menu readiness separately; at least 10 runs on each candidate machine | Report medians/p95 and failures, separate SQL warm-up/migrations; owner agrees time budget |
| Idle/peak resources | Sample working/private bytes, managed heap, native/GDI handles, CPU and GC during idle, menu images, report and print backlog | No sustained growth after repeated identical cycles; sufficient memory reserve without persistent paging |
| UI responsiveness | Synthetic 40/200/1,000-product menus, revisions, rapid Arabic typing/category changes, target DPI/display | Suggested p95 input response <100 ms and no long UI freezes; agreed target, not a claimed measured pass |
| SQL/report load | Approved isolated history sizes and station concurrency; capture actual SQL duration, logical reads, plans, grants, parameter shape and allocated rows | Same reconciled financial output; interactive p95 below client timeout with margin; no guessed indexes without plan |
| Connection outage | Controlled API latency/timeouts, then recovery; monitor probe overlap and queue/retry state | No duplicated financial commands, no hidden uncertain state, no unbounded overlapping probes |
| Printer rendering | Synthetic short/long Arabic, QR, inversion and multiple cuts; measure CPU, peak allocations, payload hashes and GDI count | No silent clipping/truncation, stable cleanup after exceptions; physical paper requires separate approval |
| Queue backlog | Approved synthetic queue, per-route single printer/file transport, report failures/crash checkpoints | Durable outcomes preserved, oldest-first fairness, no automatic duplicate physical send after uncertainty |
| Backup coexistence | Approved isolated database during peak test; quantify backup duration, disk headroom and foreground p95 | Verified recoverability and financial correctness retained; never remove backup safeguards for speed |
| Soak/capacity | Full shift-length workload on proposed low-end and recommended configurations | Bound resource growth and publish tested station/order/history limits instead of extrapolating universal capacity |

## Priorities and regression costs

First obtain reproducible stage timings/SQL plans and a sanitized resource baseline (low code risk; test-environment setup requires approval). Then address query projection/aggregation, image-version cache bounds and search rebuild cost (medium effort; financial/culture/UI correctness tests required). Health single-flight is modest effort with lifecycle/offline-state regressions. Print batching and claim/lease is a reliability/concurrency design change, not a quick performance patch; coordinate with security and printing owners. Raster optimization is higher complexity because pixel-level Arabic/QR quality and native lifetime can regress.

Do not weaken transaction boundaries, idempotency, audit retention, approval checks, session revocation, frozen receipt values, attempt persistence or production backups for lower RAM/CPU. No optimization, dependency upgrade, schema/index change, OS setting, service or financial data modification was implemented.
