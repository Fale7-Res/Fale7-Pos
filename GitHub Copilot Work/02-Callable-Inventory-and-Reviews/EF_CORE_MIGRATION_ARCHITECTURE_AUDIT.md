### 1.2 Core Audit Conclusions
1. **Provenance vs. Impact:** While 90.36% (2,605 callables) represent designer/snapshot metadata generated by tooling, the remaining 9.64% (278 callables) directly govern database schema DDL, foreign key cascade behaviors, indexing strategies, and data mutations.
2. **Critical Schema Hazards Found:**
   - **FIN-009 / Missing Open Business Day Index:** `BusinessDays` table completely lacks a filtered unique index on `[Status] = 'Open'`. Multiple concurrent open requests can produce duplicate open business days.
   - **Cascading Financial Deletion Hazards:** EF Core migrations configure `ON DELETE CASCADE` between `Orders` and `OrderRefunds`, and between `Purchases` and `PurchasePayments`. Hard-deleting an order or purchase record silently wipes out fiscal refund vouchers and supplier payment ledgers.
   - **Severe Index Gaps on High-Volume Tables:** Critical foreign key and audit columns (`TreasuryMovements.ShiftId`, `TreasuryMovements.BusinessDayId`, `TreasuryMovements.CreatedAtUtc`, `Orders.BusinessDayId`, `Orders.OrderNumber`, `StockMovements.CreatedAtUtc`) are completely unindexed, triggering full table scans during shift closeout, daily settlement, and reporting.
   - **Destructive Data Rollback in Migrations:** `20260911173753_RenameDineInOrdersToPickup.cs` contains a hand-written raw SQL `Down()` method that indiscriminately converts **all** pickup orders (even genuine pickup orders) to `dine_in`, causing catastrophic historical order corruption upon migration rollback.
   - **Irreversible PIN Destruction:** `20260904032944_DropPlaintextUserPin.cs` drops the plaintext PIN column without data backup; its `Down()` method restores empty strings (`""`), locking all users out if rolled back.

## 3. Critical Schema & Financial Hazards Audit

### Hazard 1: Missing Filtered Unique Index on Open Business Days (FIN-009)
- **Entity:** `BusinessDayEntity` (`src/Falah.Infrastructure/Persistence/Entities/BusinessDayEntity.cs`)
- **Table:** `BusinessDays`
- **Current Migration State:**
  In migration `20260903154545_AddBusinessDay.cs`, only one index was created:
  ```csharp
  migrationBuilder.CreateIndex(
      name: "IX_BusinessDays_OpenRequestId",
      table: "BusinessDays",
      column: "OpenRequestId",
      unique: true);
  ```
- **Hazard Analysis:**
  There is **NO** index on `Status`, let alone a filtered unique index on `[Status] = 'Open'`. If two concurrent requests arrive at `/api/business-day/open` with different `OpenRequestId` values, or if a network partition / retry introduces race conditions, the database engine permits two or more business days to remain concurrently open.
  This directly breaks invariant `FIN-009`: daily sales, treasury movements, and drawer reconciliations will attach to ambiguous or diverging business day IDs.
- **Shift Anomaly Contrast:**
  In migration `20260903213529_AddCustomersAndDeliverySnapshot.cs`, a filtered unique index was added to `Shifts`:
  ```csharp
  migrationBuilder.CreateIndex(
      name: "IX_Shifts_Status",
      table: "Shifts",
      column: "Status",
      unique: true,
      filter: "[Status] = 'Open'");
  ```
  While this prevents multiple open shifts, it enforces that **only one shift may be open across the entire database**, completely blocking multi-station/multi-cashier concurrency across distinct POS terminals!

In a high-throughput restaurant POS environment, ledger tables grow rapidly. The migration suite fails to index critical foreign keys and query parameters on high-volume tables:

```

| TreasuryMovements   | ShiftId                      | Shift close cash reconciliation (FULL SCAN)  |
```

**Concrete Operational Risk:**

SQL Server is forced to perform a **Clustered Index Scan** of the entire `TreasuryMovements` table. As months of operational transactions accumulate, shift closeout latency degrades from milliseconds to tens of seconds, leading to connection timeouts and deadlocks on low-spec POS hardware.

### Hazard 3: Cascading Deletes That Wipe Financial & Audit Records

An analysis of `FalahDbContextModelSnapshot.cs` and the migration DDL scripts reveals **13 Foreign Keys configured with `ReferentialAction.Cascade`**:

```
[MODEL SNAPSHOT CASCADE AUDIT]
1. OrderRefunds      -> Orders      [ON DELETE CASCADE]  <-- CRITICAL FINANCIAL HAZARD
2. PurchasePayments  -> Purchases   [ON DELETE CASCADE]  <-- CRITICAL FINANCIAL HAZARD
3. OrderItems        -> Orders      [ON DELETE CASCADE]  <-- Operational Hazard
4. PurchaseLines     -> Purchases   [ON DELETE CASCADE]  <-- Operational Hazard
5. CustomerAddress   -> Customer    [ON DELETE CASCADE]
6. PrepRecipeLine    -> PrepRecipe  [ON DELETE CASCADE]
7. PriceRuleDay      -> PriceRule   [ON DELETE CASCADE]
8. PriceRuleProduct  -> PriceRule   [ON DELETE CASCADE]
9. PriceRuleProduct  -> Product     [ON DELETE CASCADE]
10. PrintJobAttempt  -> PrintJob    [ON DELETE CASCADE]
11. ProductImage     -> Product     [ON DELETE CASCADE]
12. ProductVariant   -> Product     [ON DELETE CASCADE]
13. RecipeItem       -> Recipe      [ON DELETE CASCADE]
```

#### The Financial Destruction Scenarios
1. **`FK_OrderRefunds_Orders_OrderId` [CASCADE]:**
   In `20260902120327_InitialCreate.cs`, line 428:
   ```csharp
   table.ForeignKey(
       name: "FK_OrderRefunds_Orders_OrderId",
       column: x => x.OrderId,
       principalTable: "Orders",
       principalColumn: "Id",
       onDelete: ReferentialAction.Cascade);
   ```
   If an order record is purged, archived, or deleted via EF Core (`db.Orders.Remove(order)`), **all fiscal refund vouchers associated with that order are instantly wiped from the database without trace**. The cash drawer will reflect a payout, the treasury ledger will reflect a debit, but the underlying refund documentation is obliterated.
2. **`FK_PurchasePayments_Purchases_PurchaseId` [CASCADE]:**
   In `20260904015716_AddPurchasingAndSuppliers.cs`, line 150:
   ```csharp
   table.ForeignKey(
       name: "FK_PurchasePayments_Purchases_PurchaseId",
       column: x => x.PurchaseId,
       principalTable: "Purchases",
       principalColumn: "Id",
       onDelete: ReferentialAction.Cascade);
   ```
   Deleting a supplier purchase invoice automatically purges all payment transaction records issued to that supplier.
3. **Inconsistent Referential Integrity Architecture:**
   While `OrderRefunds` and `PurchasePayments` are marked `CASCADE`, `Delivery` correctly uses `RESTRICT` on `OrderId` (`20260903201102_AddDelivery.cs`), and `StockMovements` correctly uses `RESTRICT` on `InventoryItemId`. This confirms that the cascade settings on financial tables were scatted by default rather than designed intentionally.

### Hazard 4: Non-Reversible Down() Methods & Data-Loss Risks on Rollback

#### Hazard 4A: Historical Data Corruption in `RenameDineInOrdersToPickup.cs`
In `20260911173753_RenameDineInOrdersToPickup.cs`:
```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.Sql("UPDATE Orders SET OrderType = 'pickup' WHERE OrderType IN ('dine_in', 'dinein');");
}

protected override void Down(MigrationBuilder migrationBuilder)
{
    migrationBuilder.Sql("UPDATE Orders SET OrderType = 'dine_in' WHERE OrderType = 'pickup';");
}
```
- **Catastrophic Flaw:**
  The `Down()` method assumes that every order with `OrderType = 'pickup'` was originally `dine_in`!
  If an operator rolls back this migration to apply an urgent hotfix, **every legitimate pickup order created before or after this migration is permanently converted into `dine_in`**. Pickup orders with customer phone numbers, pickup times, and curbside notes become dine-in orders assigned to nonexistent table numbers. This is a severe, irreversible data corruption defect.

#### Hazard 4B: Irreversible PIN Erasure in `DropPlaintextUserPin.cs`
In `20260904032944_DropPlaintextUserPin.cs`:
```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.DropColumn(name: "Pin", table: "Users");
}

protected override void Down(MigrationBuilder migrationBuilder)
{
    migrationBuilder.AddColumn<string>(
        name: "Pin",
        table: "Users",
        type: "nvarchar(450)",
        nullable: false,
        defaultValue: "");
}
```
- **Flaw:**
  The `Up()` method drops the column without a fallback or archive table. If rolled back, `Down()` populates `Users.Pin` with empty strings `""`. Every employee and manager is immediately locked out because the authentication handler rejects empty PINs or hashes `""` incorrectly.

#### Hazard 4C: Nuclear Teardown in `InitialCreate.Down()`
In `20260902120327_InitialCreate.cs`:
`Down()` drops all 20 foundational database tables sequentially. A single accidental `dotnet ef database update 0` completely wipes the database, destroying all fiscal history with zero recovery safeguards.

## 5. Architectural Remediation Blueprint

To remediate these database and migration architectural hazards, the development team must implement a dedicated migration: `20261026_RemediateSchemaAndFinancialHazards.cs`.

### 5.1 Remediation DDL Specification

```sql
-- 1. Remediate FIN-009: Prevent Concurrent Open Business Days
CREATE UNIQUE NONCLUSTERED INDEX [IX_BusinessDays_Status_Open]
ON [BusinessDays] ([Status])
WHERE [Status] = 'Open';

-- 2. Add Missing High-Volume Foreign Key & Audit Indexes
CREATE NONCLUSTERED INDEX [IX_TreasuryMovements_ShiftId]
ON [TreasuryMovements] ([ShiftId])
INCLUDE ([AmountPiastres], [Type], [Status]);

CREATE NONCLUSTERED INDEX [IX_TreasuryMovements_BusinessDayId]
ON [TreasuryMovements] ([BusinessDayId])
INCLUDE ([AmountPiastres], [Type], [Status]);

CREATE NONCLUSTERED INDEX [IX_TreasuryMovements_CreatedAtUtc]
ON [TreasuryMovements] ([CreatedAtUtc] DESC);

CREATE NONCLUSTERED INDEX [IX_StockMovements_CreatedAtUtc]
ON [StockMovements] ([CreatedAtUtc] DESC)
INCLUDE ([InventoryItemId], [QuantityMilliUnits], [Type]);

CREATE NONCLUSTERED INDEX [IX_Orders_BusinessDayId]
ON [Orders] ([BusinessDayId])
INCLUDE ([TotalPiastres], [Status], [IsPaid]);

CREATE NONCLUSTERED INDEX [IX_Orders_OrderNumber]
ON [Orders] ([OrderNumber]);

CREATE NONCLUSTERED INDEX [IX_Orders_CreatedAtUtc]
ON [Orders] ([CreatedAtUtc] DESC);

-- 3. Remediate Dangerous Cascading Deletes on Financial Records
-- Drop cascade constraint on OrderRefunds
ALTER TABLE [OrderRefunds] DROP CONSTRAINT [FK_OrderRefunds_Orders_OrderId];
ALTER TABLE [OrderRefunds] ADD CONSTRAINT [FK_OrderRefunds_Orders_OrderId]
    FOREIGN KEY ([OrderId]) REFERENCES [Orders] ([Id])
    ON DELETE NO ACTION;

-- Drop cascade constraint on PurchasePayments
ALTER TABLE [PurchasePayments] DROP CONSTRAINT [FK_PurchasePayments_Purchases_PurchaseId];
ALTER TABLE [PurchasePayments] ADD CONSTRAINT [FK_PurchasePayments_Purchases_PurchaseId]
    FOREIGN KEY ([PurchaseId]) REFERENCES [Purchases] ([Id])
    ON DELETE NO ACTION;
```

### 5.2 EF Core Entity Configuration Changes
In `Falah.Infrastructure.Persistence.FalahDbContext.OnModelCreating`:

```csharp
// 1. Enforce Restrict / NoAction on Financial Vouchers
modelBuilder.Entity<OrderRefundEntity>()
    .HasOne<OrderEntity>()
    .WithMany()
    .HasForeignKey(r => r.OrderId)
    .OnDelete(DeleteBehavior.Restrict);

modelBuilder.Entity<PurchasePaymentEntity>()
    .HasOne<PurchaseEntity>()
    .WithMany()
    .HasForeignKey(p => p.PurchaseId)
    .OnDelete(DeleteBehavior.Restrict);

// 2. Filtered Unique Index on Open Business Days
modelBuilder.Entity<BusinessDayEntity>()
    .HasIndex(b => b.Status)
    .IsUnique()
    .HasFilter("[Status] = 'Open'");
```
